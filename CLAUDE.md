# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

GoodFinances (internally FinanApp/`com.finapp` — the applicationId never changes, or the installed app stops updating) — an Android personal finance app (Kotlin + Jetpack Compose, Material 3, always dark mode). **Code and UI are written in Brazilian Portuguese** (class/function/property names in pt-BR, e.g. `TransacaoViewModel.adicionarTransacao`); documentation, commit messages and tooling comments are in English.

## Build

No Java or Gradle on this machine's PATH — use the Android Studio JBR:

```powershell
$env:JAVA_HOME = "C:\Program Files\Android\Android Studio\jbr"
.\gradlew.bat assembleDebug          # debug APK
.\gradlew.bat testDebugUnitTest      # unit tests (JUnit, src/test)
.\gradlew.bat assembleRelease        # signed release APK (R8)
```

- Debug APK: `app\build\outputs\apk\debug\app-debug.apk`
- SDK path in `local.properties` (compileSdk 36, minSdk 26)
- Versions centralized in `gradle/libs.versions.toml` (AGP 8.9.2, Kotlin 2.1.0, Room 2.7.1, Hilt 2.53.1, **KSP** — do not use kapt)
- Releases are signed via `key.properties` + `finapp-release.jks` in the root (**git-ignored** — losing them means never updating the installed app again; keep a backup). Publishing steps and the auto-update contract: `docs/release.md`.
- No Android Studio? `docs/release.md` has a from-scratch JDK 17 + SDK setup.

## Architecture

MVVM + Repository, reactive throughout via Room Flows (the UI never reloads data by hand):

- `data/db/` — Room (version **17**): 7 entities (`Transacao`, `Categoria`, `ConfiguracaoPerfil`, `TransacaoRecorrente`, `Cartao`, `Meta`, `ContaAgendada`) + DAOs. Aggregations (balance, sums per category/period) happen **in SQL**, not in memory. Enums persisted by name; `LocalDate` as epoch day (`Converters`). `Meta` = savings goal (manual contributions); `ContaAgendada` = payable/receivable with a pending state → `pagarConta` creates the `Transacao` and marks it `pago`. `Transacao.pago = false` = pending (credit purchase until the invoice is paid, an expense posted by a recurrence, a future instalment without a card): it **does not count in `observarSaldoTotal`** until marked paid (row menu or "Pagar fatura" on the card group); `observarPendentePeriodo` sums the payable amount for the month shown on Home. Income and manual entries are born paid. Settling records `Transacao.dataPagamento` (v16, defaults to today; adjustable in the edit modal along with paid/pending status) and the history groups by `dataEfetiva` (payment day once paid, due date while pending) — reverting to pending clears it.
- `data/repository/FinanceRepository.kt` — the single data gateway; holds the default-category seed, posting of due recurrences, and import with dedup (date+amount+category).
- `data/PerfilManager.kt` — **the central concept**: the active profile lives in SharedPreferences, exposed as a StateFlow. `perfilAtivo` = the user's choice (PESSOA_FISICA/MEI/CNPJ, drives the layout); `perfilDados` = the **private** bucket of the active context (`MEI_PESSOAL`/`MEI_NEGOCIO` depending on the tab). All data is partitioned by the `perfil` column (one database, not one per profile).
- **The House is NOT a tab** (since the merge): Personal and House are a single view, and each entry picks **whose it is** — **only Business stays separate**. There are at most `Pessoal | Empresa` tabs. Hence the three `PerfilManager` flows, which must not be confused:
  - `perfilDados` — the private bucket; default write target and the anchor of single-bucket screens (Settings, backup, export).
  - `baldesFinanceiros` — what enters **balance/sums/pending**: private + `CASA`.
  - `baldesVisiveis` — what the **lists** read: `baldesFinanceiros` + `CASA_MEMBROS`. The difference is the member mirror: it shows in the list (so you know what happened) but **never in your balance**. Confusing the two makes another member's personal expense come out of your balance.
  - `baldesDoContexto(contexto)` expands ANY context (Analysis combines contexts); `baldeDe(dono)` resolves the write bucket; `baldeGlobal()` is where global entities (cards) are born.
- **`Dono` = whose the entry is** (`Dono.Casa` or `Dono.Pessoa(uid)`), stored in `Transacao.pessoaUid`/`pessoaNome` (v17). **Not to be confused with `criadoPor*`, which is who TYPED it**: the point of the feature is logging someone else's expense (I log my partner's, she logs mine). In a house **everything is written to `Perfil.CASA`**, including entries assigned to a person — in the typist's private bucket the other person would never see it, and the assignment would not be mutual. Explicit consequence: **in a house, an expense assigned to someone is visible to both**. Outside a house there is no choice (private bucket, empty `pessoaUid`).
  - Names come from the `nomes` map on the house doc (`CasaManager.registrarMeuNome`, a nested-field update on `nomes.<uid>` so it does not overwrite the others) — the `membros` list only stores uids.
  - Compare `Dono`/`FiltroDono` **by uid** (`mesmoQue`), never with `==`: the name stored on the transaction can diverge from the one published by the house, and the right chip would not highlight.
  - `atendeFiltro(filtro, meuUid)` needs the signed-in uid because "my expenses" come from two places: those assigned to me in the house **and** those in my private bucket (including pre-v17 ones).
  - Changing the owner while EDITING is disabled — it would disturb what already synced.
- `utils/Fluxos.kt` — `mesclarListas`/`somarBaldes` merge buckets. They **short-circuit the empty collection on purpose**: `combine` over an empty list never emits and would freeze the UI on its initial value.
- `data/sync/CasaManager.kt` — Google sign-in (Credential Manager + Firebase Auth) and the "House" (shared wallet): a `casas/{id}` document in Firestore with a 6-char `codigoConvite` and a `membros` list. `Perfil.CASA` is the local bucket for shared data; it only appears in the selector when the user is in a house. Requires `app/google-services.json` (git-ignored) — if the `default_web_client_id` resource is missing at runtime, the Google provider was not enabled in the console and the json must be downloaded again.
- `data/sync/SyncManager.kt` — the sync engine (started by `FinanApplication`): syncs `transacoes`, `categorias`, `cartoes`, `metas` and `contas` (all collective in the House; `metas`/`contas` follow the card pattern — no author guard, any member edits). Update `firestore.rules` when adding a collection. PULL via snapshot listeners on `casas/{id}/transacoes|categorias/{uuid}`, applying remote docs when the remote `atualizadoEm` is greater (a tie keeps the local row, avoiding echoes); PUSH is reactive with a debounce that uploads rows with `atualizadoEm > watermark` (prefs, per house) — fire-and-forget, because the Firestore offline queue is durable. **Rules**: pull writes go straight to the DAOs, preserving the remote `atualizadoEm` (never through the repository, which re-stamps); House default categories are seeded ONLY by the creator (`semearCategoriasCasa`) — `garantirCategoriasPadrao` skips CASA on purpose.
- `data/notif/` — `NotificacaoManager` evaluates financial triggers (due dates, DAS, budget at 80/100%, MEI ceiling, the day's recurring income, bills coming due, 3 days of inactivity) and posts local notifications, deduplicated per period in prefs; `NotificacaoWorker` runs **3x/day** (morning/afternoon/evening runs, periodic works `notificacoes_manha|tarde|noite` with an initialDelay at each hour; the legacy `notificacoes_diarias` is cancelled on scheduling) and obtains the manager through a Hilt `EntryPoint` (no HiltWorkerFactory). **Due dates** (`Vencimentos.kt`, pure and tested): a pending expense and a card invoice (grouped by card+date) warn on every run starting `DIAS_AVISO_VENCIMENTO` (5) days ahead and while overdue — deduped by day + `PeriodoDia`; recurring EXPENSES stay OUT of `avaliarRecorrentes` (the pending occurrence is already covered by due dates). Channels are created in `FinanApplication`; `POST_NOTIFICATIONS` is requested in `MainActivity` (fail-open). Toggle under Configurações › Notificações.
- `data/io/` — Export (CSV/JSON/PDF with the native `PdfDocument`), `ParserImportacao` (a pure class, no Android — this is what the unit tests cover; `ImportManager` only resolves the Uri) and the weekly Backup (every profile with data, 4 per profile, in `getExternalFilesDir` + a doc at `usuarios/{uid}/backups` in Firestore; restore filters by the active profile). `NotaFiscalManager` stores receipts in `filesDir/notas/` (any context; images are converted to PDF on the way in); `DriveBackupManager` backs those files up to the signed-in account's Google Drive `appDataFolder` (scope `drive.appdata` via AuthorizationClient — no Firebase Storage, no billing). Uses the Storage Access Framework — **no storage permissions; do not add `WRITE_EXTERNAL_STORAGE`**. External files (CSV/JSON) carry values as **decimal reais**; the conversion to cents happens in the parser.
- `viewmodel/` — one per tab + `PerfilViewModel` (initial selection + onboarding tips). Write errors become messages on a `SharedFlow<String>` collected by the UI (snackbar/toast).
- `ui/screen/` + `ui/component/` — `TransacaoModal` (a create/edit bottom sheet with the BR cents mask; category is pick-only, no typing; instalments take the TOTAL and divide) and `TransacaoLinha` (tap = edit, long-press = menu Editar/Esconder/Excluir/Encerrar recorrência — **no swipe-to-delete**) are used by Home. The bottom nav has **4 tabs**: Home (dashboard + the month's list in a single LazyColumn, month navigation, search across all months, a budget card when any category has a cap; credit purchases grouped by card via `ui/component/CartaoGrupo.kt`; filter chips `Tudo | Casa | Meu | <members>` over the unified list and an owner badge on each row; the "Próximos meses" strip with what is already scheduled — materialized pending entries, not a projection), Análise, Ônibus and Config (collapsible sections; recurrences editable by tap, except Salário/DAS which have their own fields). The Metas (`PlanejamentoScreen`) and Transações screens were removed from the UI — the `Meta`/`ContaAgendada` entities remain in the database/sync/backup for compatibility; do not recreate the screens without an explicit request. Analysis charts are plain Compose Canvas — **do not add a charting library**; the expense pie splits debit/cash by category and credit by card (`FatiaPizza.cartaoUuid`). Analysis has **combinable contexts**: multi-select Pessoal/Empresa chips (`contextosSelecionados`; empty = follow Home's active context) — `baldes` expands each context into its buckets and the flows merge via `mesclar`; the House card mirror counts as the original card (`canonicoCartao`, otherwise Personal+House would double the slice/invoice; `FatiaPizza.cartaoUuids` keeps the raw uuids for the detail view). The **Cartões** sub-tab (`VisaoCartao`/`ParteCartao`) shows everything that went through each card with the per-context breakdown and every item labelled — it **ignores the purpose chips** (it reads `Perfil.BALDES_TODOS`): a card invoice is a single invoice, wherever the spending came from.
- Theme: `FinanAppTheme(escalaFonte, corPrimaria)`, dynamic via `AparenciaManager`; dark mode is fixed.

## Conventions

- **Money is `Long` in CENTS** throughout the app (entities, ViewModels, UI). Always displayed via `utils/Formatadores.moeda(Long)` (pt-BR). Watch out for integer division when computing chart proportions (`toDouble()` first).
- **The model is built for cross-device sync** (schema v3): every entity has `uuid` (global identity, unique index), `atualizadoEm` (epoch millis, "last write wins") and `deletado` (tombstone). Rules: **deleting = setting `deletado = true`** through the repository (never a direct `@Delete` — even `deletarTodasTransacoes` tombstones, otherwise sync/the mirror resurrects the row or the cleanup never propagates; only the local `CASA_MEMBROS` mirror deletes physically); in the House, **only the author (`criadoPor`) edits/deletes** — guarded in the ViewModels via `podeSerEditadaPor`; **every write goes through the repository**, which stamps `atualizadoEm`; **read queries filter `deletado = 0`**; undo = `restaurarTransacao` (clears the tombstone, does not re-insert); transfers between contexts share a `transferenciaId` — deleting/restoring one leg affects the other (through the repository). Import dedups by uuid on top of the date+amount+category triple.
- Categories are never deleted: archiving preserves history; renaming goes through `FinanceRepository.renomearCategoria`, which propagates the new name to transactions and recurrences (categories are referenced by name, not id).
- New values in the `Perfil` enum need no migration (TEXT column), but any change to an entity requires a version bump + a migration in `AppDatabase` (see `MIGRACAO_1_2` as the template).
- Period filters use `utils/PeriodoFiltro` (weeks start on Monday). Screens that depend on "today" combine with `utils/fluxoDataAtual()` (re-emits at midnight) — never capture `LocalDate.now()` once inside a long-lived Flow.
- The fixed salary (Settings) is materialized as a monthly `TransacaoRecorrente` described "Salário fixo" — `ConfigViewModel` keeps the two in sync.
- MONTHLY recurrences store the intended day in `TransacaoRecorrente.diaMensal` (v13): a short month posts on the last day and RETURNS to the requested day next month — never reschedule with chained `plusMonths` (it truncates 31→28 forever).
- **MONTHLY recurrences materialize 12 months ahead** (`Recorrencias.kt`: `MESES_HORIZONTE_MENSAL`/`deveLancarRecorrente`/`proximaOcorrencia`/`ajustarDiaNoMes`, pure and tested): each occurrence is born `pago=false` (expense = payable, income = receivable) with `data` on the due/receipt day and a **deterministic uuid** (`uuidOcorrenciaRecorrente` — reprocessing never duplicates; the tombstone blocks resurrection) plus `Transacao.recorrenciaUuid` (v15) linking back to the rule. Monthly INCOME (salary) **auto-receives on the day** via the `proximaConfirmacao` cursor (once per occurrence — unchecking later does not re-mark). `terminaEm` = "runs until" (occurrences beyond it do not post; the recurrence ends itself). **Always edit/end a recurrence through `atualizarRecorrenteComOcorrencias`/`encerrarRecorrenteComOcorrencias`** (editing propagates in place only to unpaid occurrences with `data >= today`; NEVER re-anchor `proximoLancamento` backwards — it would repost already-materialized months). **Ending has no date cutoff**: it tombstones EVERY unpaid occurrence (`tombstonarOcorrenciasNaoPagas`), overdue ones included — that is what "ending" means to the user; with a "from today on" cutoff the past-due instalment survived and forced the user to manually delete exactly the red row that bothers them. Only "runs until" uses the cutoff (`tombstonarOcorrenciasApos`). A recurrence can be ended **from the Home row** (long-press menu "Encerrar recorrência", only when `recorrenciaUuid` is non-empty): `HomeViewModel.contarPendentesDaRecorrencia` feeds the confirmation (how many disappear) and `encerrarRecorrenciaDe` resolves the rule via `buscarRecorrentePorUuid`. There is no undo — hence the confirmation. `NotificacaoManager.avaliarRecorrentes` notifies monthly rules by `diaMensal`, not by the cursor. **Recurring expenses are created from `TransacaoModal`**: a "Repetir todo mês" checkbox on a one-off EXPENSE reveals "runs until" (pre-filled with 12 months; blank = no end) — in that case `TransacaoViewModel.adicionarTransacao` does NOT insert the standalone transaction: it creates the recurrence with `proximoLancamento = data` and calls `processarRecorrentesVencidas` right away (the month's pending entry, linked by `recorrenciaUuid`, shows up immediately; an attached receipt goes to the first occurrence). Settings only lists/edits/ends recurrences (the "+ Novo" dialog was removed on purpose — do not recreate it). Recurring INCOME keeps the old flow (posts today + a recurrence next month); manual income has a "a receber" checkbox in the modal; Home shows payable (pending expense) and receivable (pending income) separately (`observarPendentePorTipo`). **Overdue** = a pending expense with `data` in the past (a derived state, not a column): a red "Atrasado" line on `SaldoCard` (`observarAtrasado`), a label on `TransacaoItem`, "Atrasada" on the card group/invoices, and a notification per run.
- **Cards are GLOBAL, they do not belong to a context**: register one and it shows up in Personal, House and Business. What stays separate is the **spending**, by the transaction's bucket (using the same Nubank for R$ 250 personally and R$ 10 in the house adds up correctly under each filter). `Cartao.perfil` only decides what syncs — a new card is born in `PerfilManager.baldeGlobal()` (the personal side of the mode, even when created on the Business tab), which is what mirrors it to the House. The repository exposes **two deliberate views**: `observarCartoesGlobais()` in a **RAW** state (mirrors included — resolving which card a House purchase belongs to requires seeing them, since it points at the mirror's uuid) and `observarCartoesParaEscolha()` already collapsed (the picker must not show "Nubank" twice). `utils/Cartoes.kt` centralizes `canonicoCartao`/`cartaoPorCanonico`/`cartoesUnicos` — **grouping without canonicalizing splits one invoice into two groups**.
- **Personal cards also appear in the House through a mirror** (v14, `Cartao.origemUuid`): `FinanceRepository.sincronizarEspelhoCartaoNaCasa` upserts a `perfil=CASA` row with a deterministic uuid (`uuidEspelhoCartao`) on every insert/update/delete of a card in `BALDES_PESSOAIS` (business is excluded); reconciliation happens in `CasaManager.carregarCasa/criarCasa/entrarNaCasa` via `espelharCartoesPessoaisNaCasa`. One-way original→mirror: in the House the mirror is **read-only** (guards in `ConfigViewModel` + no "Remover" on the `ConfigScreen` row). On `sairDaCasa`, tombstone the mirrors directly in Firestore BEFORE the `arrayRemove` (otherwise they become orphans on the other members' devices). The repository learns about the house through `PerfilManager.temCasa()` (do not inject `CasaManager` into the repository — DI cycle).
- **The bus tab debits itself on routine days** (`OnibusManager`): `calcularDescontosOnibus` (pure, tested) uses the `onibus_ultimo_dia_processado` cursor + `EstadoDiaOnibus` (per-leg `usada`/`processada` flags — unchecking a `processada` leg does not debit it again); the outbound leg from `horaIda`, the return from `horaVolta`; never below zero (a leg with no balance is marked processed but unused, it does not go into debt). Triggers: `OnibusViewModel`/`HomeViewModel` (via `fluxoDataAtual`) and `NotificacaoWorker` — idempotent by design. `projetarOnibus` takes `usadasHoje` so today is not counted twice.
